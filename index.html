📖 Replica Set in READ-ONLY mode — no downtime
The replica set has fallen below majority quorum. The database is still fully available for reads — no downtime has occurred. Writes are temporarily suspended to prevent data inconsistency. As soon as enough nodes come back online and majority is restored, writes resume automatically.
🔴 Complete outage — all nodes are DOWN
Every node in the replica set is unreachable. No reads or writes can be served. This is a full database outage. Restore at least one node to resume reads, and restore majority to resume writes.

Write & Read Concerns
Write Concern controls durability — how many replica set nodes must confirm a write before the driver returns success. Read Concern controls data freshness — whether you see only majority-committed data or also in-flight writes. Read Preference controls which node serves the read. Adjust any setting to see how MongoDB's CAP position shifts.

⚠ 2-Region topology — quorum limitation
Each shard distributes as 2 nodes in the home region + 1 in DR. If the home region fails, the surviving DR node holds 1 of 3 votes — below majority. That shard enters READ-ONLY mode automatically. This is deterministic: no concern setting changes it within 2 regions.
✦ MongoDB recommendation: always deploy across 3 or more regions to guarantee majority quorum survives any single-region failure with no manual intervention.
MongoDB Global Cluster uses Zone Sharding to pin each region's data to a dedicated shard — every Backend writes to its local Primary, achieving true Active-Active with minimal latency. Cross-region oplog replication keeps data durable. Select a deployment pattern and simulate a zone or a region failure to see exactly which shards lose write access and why.
